# CU17 y CU18 — Revisión inteligente y modificaciones UML

## CU17: revisión inteligente

La acción **Revisar diagrama con IA** crea una solicitud `REVISION_UML` dentro del chat compartido del proyecto. El informe se persiste como metadatos del mensaje IA e incluye diagrama, versión, fecha, solicitante, resumen y hallazgos clasificados.

La revisión combina:

- reglas deterministas para integridad referencial, duplicados y multiplicidades;
- análisis semántico del proveedor IA para cohesión, acoplamiento y diseño de dominio.

Los hallazgos semánticos deben citar evidencia del `modeloJson`. Una hipótesis de dominio se clasifica como sugerencia, no como error formal. Las recomendaciones quedan ligadas a la versión exacta del diagrama y la interfaz las marca como obsoletas cuando esa versión cambia.

El ciclo visible de una propuesta distingue pendiente, aplicada, descartada y obsoleta. Descartar persiste el identificador en el mensaje IA, registra bitácora y publica un mensaje de sistema compartido, pero no modifica ni versiona el diagrama.

`AGREGAR_CLASE` es la única operación que no exige un ID existente. Puede proponer nombre, responsabilidad, justificación, miembros, posición y relaciones con clases existentes. Ninguna propuesta modifica el modelo sin confirmación.

### Relaciones y causa del descarte anterior

El contrato anterior enumeraba `AGREGAR_RELACION`, pero exigía que toda operación distinta de `AGREGAR_CLASE` tuviera el ID de un elemento ya existente. Como una relación nueva todavía no posee ID, el parser descartaba silenciosamente la propuesta aunque el proveedor la explicara correctamente. La sanitización también rechazaba nombres de clases propuestas en la misma respuesta.

Ahora `AGREGAR_RELACION` identifica su clase origen existente, normaliza ambos extremos a UUID reales cuando ya existen y conserva por nombre únicamente una dependencia inequívoca todavía pendiente. El contrato exige origen, destino, tipo, multiplicidades, descripción y justificación. Una respuesta meramente textual no se convierte artificialmente en tarjeta.

Una asociación N:M directa se considera UML válido. La clase intermedia solo se recomienda cuando los requisitos aportan evidencia de información propia de la asociación, como fechas, estado, cantidad, historial o reglas. En ese caso se generan propuestas coordinadas `AGREGAR_CLASE` y `AGREGAR_RELACION`; las relaciones pendientes se revalidan después de crear sus clases y el backend sustituye los nombres por UUID antes de persistir.

## CU18: modificación autorizada

El backend recupera la recomendación original desde el mensaje IA; no acepta una mutación UML arbitraria enviada por el cliente. Después valida membresía, permiso de edición, versión e idempotencia.

Operaciones soportadas:

- clases: agregar, renombrar y eliminar;
- atributos: agregar, modificar y eliminar;
- métodos: agregar, modificar y eliminar;
- relaciones: agregar, modificar, eliminar y cambiar multiplicidades.

Los IDs de clases, atributos, métodos y relaciones nuevas se generan con UUID en el backend. Se rechazan nombres o relaciones duplicadas, multiplicidades inválidas, referencias inventadas y recomendaciones obsoletas. Eliminar una clase requiere confirmación especial y elimina sus relaciones dependientes dentro de la misma transacción.

La aplicación en lote ordena clases antes que relaciones y repite la revalidación mientras se resuelven dependencias. El lote autorizado usa una sola transacción y una sola persistencia/versionado del diagrama; cualquier excepción durante las operaciones aplicables provoca rollback.

Después de `saveAndFlush`, se registra bitácora y chat. `DIAGRAM_MODEL_UPDATED` se publica `AFTER_COMMIT`; los editores limpios reemplazan React Flow con el modelo persistido completo y los editores con cambios locales conservan su trabajo.
